Source sections 2, 4–6 and 19 assign Agent HQ ownership of user/AuthIdentity mapping, RuntimeNode registration, pairing and product key lifecycle. The current repository also has a concrete hosted validation path: the production `runtime-gateway` entry point loads operator-controlled Ed25519 issuer public keys, requires PostgreSQL composition, and wires `PostgresRuntimeNodeIdentityValidationPort` into WebSocket authentication. That adapter verifies operator-signed credentials against persisted node keys and credential/revocation records; it does not issue credentials. `SyntheticRuntimeNodeIdentityAuthority` is used by tests and is not imported by the production composition. These facts correct the older synthetic-identity description without transferring Agent HQ product identity or pairing ownership to Control Plane.

Live Agent HQ pairing, operator credential issuance/provisioning operations, packaged desktop key storage, and exact-candidate deployment evidence remain separate gates. The source-to-code note establishes the reachable verifier path only; it does not upgrade ledger classifications or close the retrieval/reconciliation umbrella.

Earlier inspection prose treated the injected test server and synthetic issuer as the only reachable path. Current code has a separate production `runtime-gateway.start` path: it rejects an injected WebSocket server and SQLite in production, loads required operator public keys for PostgreSQL, and composes durable credential, key, and revocation validation. This establishes the code-level verifier path only. The gateway does not issue credentials; production deployment evidence, live key provisioning, end-to-end pairing, and artifact-backed terminal results still require exact-candidate evidence before the gap can close.
